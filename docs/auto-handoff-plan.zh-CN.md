## 2026-10-28 凭证来源纠正

只读确认本机 CC Switch 为 4.0.21。核对该版本公开源码发现：`codex-login-stash.json` 保存的是被移走的原生登录副本，托管账号登录不进入此暂存；托管直连切换通过账号管理器取得同一代的完整 token bundle（必要时由管理器刷新），再由写入流程生成 `auth.json`。因此小助手仅查找现存完整登录快照，不能替代 CC Switch 的托管切换流程；快照与账号库不一致不构成必须重新登录的证据。已纠正错误提示，撤回先前将重新登录作为默认下一步的建议。

下一步应在 Desktop 完全退出后，用 CC Switch 的正常切换路径生成目标登录记录，检查账号及配置改动，再恢复原会话。自动化接入需核实外部可调用入口；内部 `get_valid_token_bundle_for_account` 不等于已有公共 API。若没有现成入口，再评估最小本机桥接；不直接拼接不同代次字段，也不假装文件快照就是管理器状态。

参考：[CC Switch 4.0.21 登录暂存](https://github.com/farion1231/cc-switch/blob/v4.0.21/src-tauri/src/services/provider/codex_login.rs)、[直连切换](https://github.com/farion1231/cc-switch/blob/v4.0.21/src-tauri/src/services/provider/codex_direct.rs)、[OAuth 管理器](https://github.com/farion1231/cc-switch/blob/v4.0.21/src-tauri/src/proxy/providers/codex_oauth_auth.rs)。

```text
用户选择原会话并手动开启
  → 当前账号五小时剩余 < 10%
  → 确认备用账号认证有效、五小时剩余高于阈值、周额度可用
  → 登记本次交接，固定原会话 ID、触发轮次、源／目标账号及执行设置
  → 请求原任务在安全边界收尾，简记断点并结束本轮
  → 必要时中断准确轮次；确认轮次与相关工具／后台命令状态
  → 正常退出旧 Codex 实例，等待退出完成
  → 再读最新目标认证，按 CC Switch 思路切换目标目录的认证
  → 启动新实例，核验实际账号及原会话执行设置
  → 恢复固定的原会话，登记并发送一次继续
  → 确认新轮次开始，结束本次交接
```

备用账号不可用时，在停任务之前取消本次交接，不在两个低额度账号间来回切。切号模块的恢复副本、原子写入与回查需要实现，但不另建长期凭证库。

## 停稳与断点

优先向准确原会话发送一次交接指令：在当前操作安全边界结束本轮，不启动新的长任务，简述已完成／待完成工作及仍在运行的命令。断点留在原聊天，不额外复制聊天正文。

这只是请求，不能作为已停止的证据。要观察轮次结束、工具调用结束，并检查相关后台命令。任务没有及时收尾、没有额度再生成总结时，中断准确当前轮次并等待确认；不要求总结成功后才能交接。无法确认停稳时暂停交接，不直接杀进程。

后台命令不等于应该被停止：能否保留、是否影响退出／重启需按实际任务判断。重启不能保留任意进程内存或保证命令从原指令位置恢复；恢复后先核对文件和运行状态，再接着工作。

## 恢复与最小持久状态

持久状态至少包含：原会话 ID、触发轮次 ID、来源（Desktop／CLI）、源／目标账号标识、原工作目录与模型／推理／权限设置、交接阶段、继续消息的登记及确认结果。只保存必要元数据，不保存 Token 或第二份聊天正文。

会话在交接开始时固定，重启后不使用“最近的聊天”、列表位置或窗口标题找目标。账号 B 生效、正确原会话就绪后，才发送一次继续，并观察到新轮次开始。

只恢复本次自动交接暂停且仍获授权的任务：正常完成不额外发继续，用户手动停止／关闭功能／改变目标时取消过时交接。继续发送结果不明确时先核对是否已开始，不能盲目重发；界面显示实际卡在哪个阶段。

## Desktop 与 CLI 的边界

- 最初建议先实现 Desktop；用户后续接受先完成可控的托管 CLI 完整路径，再接入 Desktop。两者共用状态与去重逻辑，验收分开记录。
- Desktop 需要检查共享应用内其他正在执行的聊天；不为一个会话强行退出所有聊天，先等待其他任务停稳。
- 托管 CLI 只重启其自有后端与客户端，使用原会话 ID 与原目录；普通已有终端不可假定能直接接管。
- 两端分别使用自己的认证／历史目录，不合并 `~/.codex` 与 `~/.codex-cli`，不临时改 CC Switch 的全局目录来回切换。实施时重新核实当前目录与认证存储方式。

## 尚需解决或验证的具体问题

1. 备用账号完整有效认证如何取得。CC Switch 账号列表／refresh token 记录不等于完整可用的 Codex 登录材料，访问令牌可能仅在其内存中；不能盲目复制账号记录。凭证不可用时按用户要求提示更新，不偷偷自行刷新。
2. CC Switch 管理的配置选择与 Codex 实际运行账号可能不同。小助手需显示实际核验结果；是否同步 CC Switch 的“使用中”尚未确定，不把外改其数据库视为已决定的方案。
3. 主动收尾、准确轮次中断、工具／后台命令停稳，以及退出超时的处理。
4. Desktop 重开后准确加载原聊天、原配置和实际新账号的核验，不能由磁盘文件变化推断成功。
5. 凭证切换的原子写入、旧进程退出写回、并发手动换号和失败恢复。

## 后续最低验收

- 用可控测试会话验证触发阈值、备用账号可用性，证明不可用时不会先停任务。
- 跑通主动收尾路径与无总结时的中断路径，区分请求已接受与实际已停稳。
- 实测退出、换凭证、重启、实际新身份、原会话 ID、原目录／模型／权限及新轮次开始。
- 验证用户手动介入、正常完成、其他活跃聊天、重启失败及发送结果不明确，不重复切号或续跑。
- Desktop 与 CLI 分别记录“模拟／协议检查／实机行为／未验收”，不能互相代替。
