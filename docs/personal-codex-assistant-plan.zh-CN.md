# Codex 小助手：个人需求与实施计划

记录日期：2026-10-26；最新需求确认：2026-10-27（Asia/Singapore）。

状态：0.3.0 / build 9 包括登录后启动与不切号的指定会话续跑。0.3.5 已接入托管 CLI 自动切号；0.3.6 为 Desktop 同账号续跑增加保护；0.3.7 已接通并安装 Desktop 单会话切号，模拟来源低额度条件下真实交接通过，日常使用仍需安装版辅助功能权限。实际实现与验证边界见[版本记录](macos-helper.zh-CN.md)、[会话续跑说明](resume.zh-CN.md)及[自动切号交接记录](auto-handoff-plan.zh-CN.md)。本文件保留前期需求演变，以专门交接记录中的最新检查点为准。

## 最新优化方向（2026-10-27，已确认；本轮仅记录）

用户要求：个人使用优先，不扩展为通用账号管理工具；允许重启。默认在当前账号五小时**剩余额度低于 10%**时，为手动选定并开启的会话执行“准备备用账号 → 主动收尾／中断并停稳 → 正常退出旧实例 → 切换凭证 → 重启 → 核验目标账号 → 恢复准确原会话 → 继续一次”。阈值保留可修改输入；不必等到明确限额错误后才交接。

优先参考 CC Switch 的官方账号凭证切换思路，在小助手实现必要的窄范围逻辑；不把修改或重新安装 CC Switch、增加其本机接口作为前置条件。CC Switch 仍负责登录和凭证更新，过期或目标认证不可取得时提示用户处理；小助手不自行轮换 refresh token。

重点是任务交接，不是增加账号管理：优先让任务在安全边界收尾、简记断点并结束本轮；收尾失败或额度已耗尽时使用准确轮次中断，随后确认工具／后台命令状态，不能用“已发停止请求”代替“已停稳”。重启后按固定会话 ID 继续，保持项目、模型及权限；不恢复用户手动停止、正常完成或未授权的任务，防止重复续跑。

下一步建议先完成 Desktop 一条可控的端到端交接验证，再适配托管 CLI；CLI 与 Desktop 分别验收。没有新增防休眠、唤醒恢复或其他高级设置。本次用户仅要求保存记录，未要求执行后续优化、切号或重启。

下文第 3、5、7 节保留前期方案背景；其中“必须通过 CC Switch 服务”“只在明确触限后切号”“默认先 CLI”等旧建议，以本节及专门优化记录为准。CC Switch 界面选择是否同步、备用凭证可取得性等尚未验证的技术问题，不作已解决处理。

## 0.3.0 实施范围（2026-10-26 历史交付）

用户要求优先完成登录后自启动与指定会话续跑，暂缓切号；凭证仅依靠 CC Switch 更新，过期时直接提示；不需要唤醒恢复。下文的切号需求保留为历史目标，不属于 0.3.0 交付范围。0.3.0 的使用方法与验证边界见[会话续跑](resume.zh-CN.md)。

## 1. 已确认的目标

使用者有两个 Codex Plus 账号，日常通过 CC Switch 管理和切换。希望保留现有账号与聊天历史管理方式，自动化以下两个过程：

1. **按账号自动触发五小时窗口。** 从 CC Switch 取得管控的账号信息；发现旧窗口已重置，或新窗口尚未由首条请求启动时，发送一次小请求，使其进入倒计时。
2. **为手动指定的会话自动换号续跑。** 用户明确开启此功能并选择一个对话；该对话遇到额度限制后，自动完成“引导或暂停 → CC Switch 切号 → 继续原对话”。

CLI 和 Codex Desktop 都是目标使用场景。两端需分别验证接入与续跑，不能将 CLI 的成功视为 Desktop 已验收。

优先级：先保证窗口触发与指定任务的恢复可用，再完善自动切号的异常处理。不要将范围扩大为通用账号管理平台。

## 2. 软件形态与交互

- 提供独立的 macOS 小应用，参考本机“Claude 网络助手”的紧凑原生窗口形态；用户通过双击和窗口按钮完成日常操作。
- 不以终端命令作为日常使用的主要入口，也不要求所有操作都必须在 CC Switch 界面中进行。
- 界面分别提供“自动触发五小时窗口”与“指定会话自动切号”的控制，两者独立。
- 自动切号默认关闭。选择会话不等于开启，用户还需明确点击开启。
- 更换受管会话时，自动切号恢复为关闭，不能沿用上一个会话的开启状态。
- 可查看当前账号与备用账号的额度、窗口状态、受管会话和交接结果；复杂日志与高级参数放在次要入口。
- 暂不新建完整的账号编辑、供应商管理或聊天管理界面。

### 会话选择

参考并尽可能复用 CC Switch 的会话列表与解析规则：

1. 优先显示已有标题，包括重命名后的标题。
2. 没有标题时，显示第一条有效用户问题。
3. 信息缺失时，按现有规则用项目名称等信息兜底。

列表附上项目与最近活动时间以区分同名会话。内部以准确的会话 ID 绑定；标题变化不能使绑定失效，不能用“最近一次聊天”代替用户选择的会话。运行客户端与实例需在接入时识别，不能仅凭历史文件推断当前执行身份。

前序展示过的可点选窗口仅为使用示例数据的界面示意，不代表已连接真实账号或已安装 GUI 应用。

## 3. CC Switch 复用原则

**尽可能读取现有数据、复用现有代码与服务；不重复维护第二套账号、凭据或聊天记录。**

| 内容 | 现有来源或能力 | 处理原则 |
| --- | --- | --- |
| 账号列表及身份信息 | `$HOME/.cc-switch/codex_oauth_auth.json` | 读取所需元数据，沿用账号标识 |
| 供应商名称、排序、图标和当前选择 | `$HOME/.cc-switch/cc-switch.db` | 只读获取，尽量与 CC Switch 一致 |
| Codex 配置目录与历史统一设置 | `$HOME/.cc-switch/settings.json` | 跟随现有设置，不将历史目录假设写死 |
| 会话 ID、标题、首个问题、项目、记录路径、恢复命令 | CC Switch 会话扫描与解析逻辑 | 复用规则或代码，读取同一份源数据 |
| 各账号实时额度 | 现有按账号查询额度的实现 | 优先复用，不另写一套额度解释规则 |
| 托管凭据与账号切换 | 现有认证管理器、账号绑定和供应商切换流程 | 沿用其协调机制，不绕开服务直接改文件 |
| 聊天历史统一与续会话 | 用户现有配置和 Codex/CC Switch 机制 | 不再建立聊天记录副本或额外同步系统 |

CC Switch 的会话列表来自其对 Codex 等工具现有资料的读取，不意味着全部聊天都存储于 CC Switch 数据库。应沿用它的目录发现、索引、数据库及会话解析规则。

区分两种复用方式：

- 文件或数据库已有的数据：优先只读读取。
- 实时查询、认证刷新、账号切换：优先调用现有服务；存在内部方法不等于已提供外部调用接口。

需要适配时，采用最小范围的接入层。是否必须为 CC Switch 增加本地接口或少量补丁，尚待验证；当前没有决定替换已安装的 CC Switch，也未决定将交接功能完全搬到其界面内。

新软件只保存自己的配置与自动化状态，例如受管会话、允许使用的账号标识、当前交接阶段、恢复动作是否已发送及操作结果。账号新增、删除、重命名以及会话标题变化应从现有来源刷新，不要求用户在两个软件中重复维护。

## 4. 五小时窗口自动触发

目标是窗口可用时尽早开始计时，不能强制重置服务器额度，也不能增加周额度或囤积未使用窗口。

推荐流程：

1. 读取 CC Switch 管理的 Codex 账号，分别查询实际窗口与重置时间。
2. 窗口正在运行时等待；旧窗口已重置或尚未启动窗口时，判断是否适合发送请求。
3. 按该账号身份通过官方 Codex 执行一次小请求。
4. 再次读取窗口状态，确认计时已开始；不能只把进程退出成功当作窗口已启动。

实现要求：

- 每个账号有独立调度状态，并识别同一身份，避免重复预热。
- 预热备用账号时，不临时切走正在工作的主环境账号。
- 正常工作已经触发窗口时，不额外发送重复 ping。
- 周额度耗尽或账号不可用时，等待恢复或给出对应状态。
- Mac 睡眠期间不承诺准点执行；唤醒后重新查询。
- 记录真实请求是否发出及其用量；最小提示不代表总输入只有几个 token。

备用账号的独立短暂执行环境及其与 CC Switch 认证管理器的协作方式，需要技术验证，尚未定案。

## 5. 指定会话的自动切号

### 5.1 开启范围

用户手动选择会话并开启；允许使用的账号来自 CC Switch。未开启的会话不自动暂停或续跑。关闭开关停止后续自动交接，不因此中断已经运行的任务。

### 5.2 推荐触发条件

| 情况 | 推荐动作 |
| --- | --- |
| 额度接近耗尽，但任务仍正常执行 | 查询备用账号、准备交接，不立即强行切号 |
| 指定会话明确因额度停住，查询也确认相应限额 | 执行交接 |
| 额度耗尽，但工具调用仍在完成 | 等待停稳或正常中断，不直接杀进程 |
| 额度耗尽，但会话没有因限额中断的待恢复任务 | 不凭额度变化自动发送“继续” |
| 网络错误、认证失效、上下文问题或等待用户输入 | 按相应原因处理，不统一归类为额度问题 |
| 无备用账号可用 | 等待最早可用额度恢复，避免来回切换 |

优先使用指定会话的结构化限额事件，并结合实时额度确认；普通 HTTP 429 或账号百分比不足以单独证明该会话需要交接。

前序讨论中的“剩余 5% 开始准备”“备用账号至少剩余 10%”仅为建议参数，不是用户最终确认的固定数值。后续应可配置，并根据实际使用验证。

### 5.3 推荐交接顺序

```text
监控指定会话
  → 确认因限额停住
  → 记录会话与当前轮次，锁定本次交接
  → 检查备用账号可用性
  → 确认原任务已停稳
  → 调用 CC Switch 原有切换流程
  → 确认执行实例使用了目标账号
  → 恢复准确的原会话，发送一次继续消息
  → 确认新轮次开始，登记交接结果
```

- 默认优先直接暂停并继续同一会话；“先让模型整理断点”作为可选方式，不能要求已经限额的模型必须再完成一轮总结。
- 沿用原模型、工作目录及权限/工具配置，不因切号擅自降低模型或扩大权限。
- 账号 ID、供应商卡片 ID 与会话 ID 是不同标识，适配层需正确对应。
- 以运行实例的实际身份确认切换，不能只检查磁盘文件或 CC Switch 界面状态。
- 恢复动作需去重；不明确时先检查是否已经开始，避免重复输入“继续”。
- 用户已经手动切号、继续或关闭功能时，协调器应重新核对状态，不能继续执行过时交接。

### 5.4 共享环境边界

“仅管理指定会话”不等于“账号切换仅影响该会话”。CC Switch 管理的配置和后端可能被多个对话共用。

若切换必须重启共享后端，而其他对话仍在执行，推荐延后交接并提示用户，不为单个受管会话强行中断其他对话。CLI 与 Desktop 的认证更新、重连和原聊天界面同步都需实测，当前未宣称可用。

## 7. 实施顺序与验收目标

1. **先验证接入：** 会话标题与 ID、指定账号额度、原有切换服务、CLI/Desktop 会话控制入口。未确认的接口保持为待验证项，不按已可调用设计。
2. **做独立小窗口与只读数据接入：** 展示现有账号和会话，验证重命名、同名区分及选择后手动开启；先不启用真实自动操作。
3. **验证双账号预热：** 真实请求后确认窗口，证明备用账号预热不会切走主环境。
4. **验证指定会话交接：** 从 CLI 开始，再分别完成 Desktop 验证；包含成功、备用账号无额度、用户手动介入、重复事件等情况。

最低验收应证明：

- 用户不用终端即可查看与操作；数据与 CC Switch 及源会话一致。
- 未开启的会话不被自动续跑；标题变化不会误绑。
- 两账号按实际窗口独立触发，不额外反复 ping。
- 指定会话触限后能够切到可用账号并继续同一会话。
- 不重复续跑，不因一般网络错误切号，无账号可用时正确等待。
- 其他运行中对话不被自动强制中断。
- CLI 与 Desktop 分别给出“已验证/未验证”结果。
